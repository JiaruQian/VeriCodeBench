# Code-Only Oracle Contract Benchmark Design and Implementation Plan

This document records the specification boundaries of the current full-chain benchmark and plans the `code_only_contract` data and code-only pipeline for the C/ACSL backend. This document first serves the C implementation; once it is completed and validated, the same principles can be migrated to the Java/JML, Rust/Verus, and Python/Nagini backends.

## 1. Background and Goals

The main task of the current benchmark is full-chain generation:

```text
Requirement -> Generated Function Contract -> Generated Code + Proof Annotations -> Verifier
```

The main evaluation checks two properties at the same time:

1. Whether the generated code satisfies the function contract generated by the model itself;
2. Whether the generated function contract covers the manually constructed ground-truth semantic targets.

This design preserves the real impact of specification-generation errors propagating into the code-generation stage, and is suitable as the main task of the paper. To further localize the source of failures, an isolated code-only diagnostic task is also needed: fix a manually constructed function contract that can be used by the verifier, and evaluate only the model's ability to implement the code and synthesize proof annotations.

The new diagnostic task is defined as:

```text
Requirement + Signature + Oracle Function Contract
    -> Generated Code + Implementation-Level Proof Annotations
    -> Verifier
```

This document uses **oracle function contract** to denote the manually constructed function contract in the code-only input, to avoid confusing it with the "complete ground-truth program specification" that includes loop invariants and the full proof scaffolding.

## 2. Current Implementation Status

### 2.1 Existing Specification Layering

The current C pipeline already distinguishes two kinds of specifications in its data structures and prompts.

The first kind is the canonical function contract:

```text
requires
assigns
ensures
```

It is stored in the `acsl_block` of the spec artifact, directly above the target function. The requirement coverage evaluation is performed only on this layer.

The second kind is implementation-level proof annotations:

```text
loop invariant
loop assigns
loop variant
assert / ghost state / other statement annotations
```

They depend on the concrete implementation, should be located in the function body and near the corresponding loops, do not belong to the function contract, and do not participate in the current main requirement-spec coverage metric.

### 2.2 Current State of `code_annotation_hints`

The current spec generation artifact may also contain:

```json
{
  "code_annotation_hints": {
    "loop_invariants": [],
    "loop_assigns": [],
    "loop_variants": []
  }
}
```

These fields are non-binding candidate hints, not the canonical function contract. The code-generation stage may reference them; verification-guided repair, especially Verifier-Guided Candidate Repair (VGCR)-style repair, may modify the function body and statement-level annotations, but must freeze the `acsl_block`.

Therefore, a more accurate description of the current system is: the specification stage generates a frozen function contract and may provide non-binding proof hints; the concrete loop annotations are generated along with the implementation and can be repaired under verifier feedback.

### 2.3 Strict Incremental Repair Is Already in Place

The current `VGCR` and `CodeNova` configurations, in both their simple and candidate repair variants, use `REUSE_ARTIFACTS_FROM` to reuse the frozen spec and initial code. Repair is only allowed to update the function body and implementation-level proof annotations, and cannot manufacture a verification pass by weakening the function contract.

Existing experimental artifacts show that between matched generation/repair runs the spec artifact remains unchanged while the code artifact changes. This principle should be reused directly for the code-only pipeline.

### 2.4 Purpose and Limitations of the Existing Manual Ground Truth

The current file:

```text
benchmarks/frama-c-problems/requirements/requirements_100_ground_truth_specs.json
```

is mainly used for requirement coverage evaluation. Each problem contains atomic `ground_truth_clauses`, whose types include `requires`, `assigns`, and `ensures`.

These atomic targets express the requirement semantics that need to be evaluated, but one cannot directly assume that they already form a verifier-ready code-only contract. The reasons include:

- The goal of the coverage ground truth is semantic scoring, not providing a directly executable unified contract;
- For some problems, `ground_truth_contract` is empty;
- The function-level conditions required to prove memory safety, arithmetic safety, or normal termination may not have been included in the coverage targets;
- Atomic clauses require a definite order, behavior structure, and legal ACSL wrapping;
- The reference contract may mix in proof annotations bound to the reference implementation, and cannot be copied wholesale to the model.

Therefore, one cannot simply take all ACSL annotations from the reference source as code-only input, nor concatenate coverage clauses without validation and use them directly in formal experiments.

### 2.5 Reference Source Is the Preferred Contract Source

The 100 reference programs of the C benchmark are located at:

```text
benchmarks/frama-c-problems/ground-truth
```

These programs have already passed Frama-C/WP during the benchmark construction stage. The function-level ACSL above the target function is therefore the preferred source for constructing `code_only_contract`: it is usually more complete than reassembling a contract from atomic coverage targets, and it has already passed verifier checking together with at least one correct implementation.

Static inspection of the current directory further indicates that "targeted extraction" should be used rather than copying entire reference files:

- All 100 reference C files can serve as candidate sources;
- 45 files contain loop annotations;
- 48 files contain additional assertions or test-helper content;
- 48 files contain multiple ACSL blocks;
- 5 target-function contracts use `behavior`;
- For 27 problems the manual JSON `ground_truth_contract` is empty, but a function contract exists in the reference source.

Therefore, the default direction for data construction is adjusted to:

```text
Reference target-function contract
    + Atomic ground-truth alignment/audit
    + Necessary manual correction
    -> code_only_contract
```

The reference source provides verifier-ready candidate contracts; the existing atomic ground truth continues to play the role of requirement-semantic audit and coverage target. The two cannot substitute for each other.

### 2.6 C Track Implementation Status

The C track has completed the construction of 100 code-only contracts, contract consistency checking, code generation, and the incremental repair pipeline. The canonical data is located at `benchmarks/frama-c-problems/requirements/requirements_100_code_only_contracts.json`, the run entry point is `scripts/run_c_code_only_pipeline.py`, and the oracle consistency report is `reports/oracle_contract_consistency.json`. This report is used to confirm that freezing the contract is not equivalent to requirement semantic coverage; the latter is still handled by the Constraint Entailment Framework (CEF).

During construction, the manual clauses of 23 C problems were revised, and the ACSL parser was extended to avoid false negatives caused by formatting differences. Although the GCD divisibility target of task 42 has been retained in the oracle semantics, the reference WP still times out; therefore this problem should be recorded as an oracle validation/proof issue and must not be bypassed by deleting the target or using an overly strong `requires`.

### 2.7 Rust/Verus Track Implementation Status

The Rust track has targeted-extracted function-level `requires/ensures` from 100 reference target-function headers, producing canonical data at `benchmarks/rust-verus-problems/requirements/requirements_100_code_only_contracts.json`. The reference clauses and curated `ground_truth_clauses` of all 100 problems correspond exactly one-to-one, so the current Rust oracle needs no additional verifier-only preconditions and has no manually modified contracts.

Rust contracts belong to function-header syntax, and the pipeline freezes three things: the canonical function signature after the named return value, the `code_only_contract` text, and the structured `verus_clauses`. The 12 reference loop invariants and 12 `decreases` clauses are all retained in the reference function body for data acceptance, but do not enter the model input. The run entry point is `scripts/run_rust_code_only_pipeline.py`, and the consistency check is `scripts/evaluate_rust_code_only_oracle.py`; the check covers both the spec artifact and the final Rust source. The current reference validation is `100 pass / 100 total`.

## 3. Specification Boundaries of the Code-Only Task

### 3.1 What Should Be Provided to the Model

The code-only input for each problem should contain:

- the original natural-language requirement;
- the fixed function signature;
- the verifier-ready oracle function contract;
- the necessary type, struct, or global declaration context;
- the basic verifier/toolchain description consistent with all methods.

The oracle function contract should fully contain the obligations at the function-interface level:

- semantic preconditions;
- memory-validity, separation, and necessary input-safety conditions;
- semantic postconditions;
- frame conditions, such as `assigns`;
- behavior completeness/disjointness when needed;
- overflow or exceptional-behavior constraints related to the function interface.

Here "complete" means complete with respect to the function caller, not exposing the entire proof process of some reference implementation to the model.

### 3.2 What Should Not Be Provided to the Model

The following must be excluded from the oracle input:

- reference loop invariants;
- reference loop assigns;
- reference loop variants;
- reference assertions inside the function body;
- ghost variables and lemmas bound to the reference implementation;
- the reference implementation itself or any proof skeleton that can directly reconstruct its control flow;
- repair hints leaked in advance by subsequent verifier failures.

These belong to the objects being evaluated in code/proof synthesis. The model may construct them on its own during initial generation, or they may be modified by simple repair or VGCR-style repair while keeping the oracle contract unchanged.

### 3.3 Why Complete Reference Annotations Cannot Be Provided

Loop invariants are determined by the concrete algorithm. The same function contract may be satisfied by a forward loop, a backward loop, multiple loops, recursion, or a loop-free implementation. Providing the loop invariants of the reference implementation leaks the algorithm structure and turns the code-only task into a program-completion task given a proof skeleton.

Therefore, what this benchmark isolates is:

> Given a correct function-interface contract, can the model jointly generate the implementation and the implementation-related proof annotations and pass the verifier?

It should not be described as "generating code given a complete formal proof."

## 4. `code_only_contract` Data Design

### 4.1 Suggested Storage Approach

For the first version, new fields can be added to the existing 100-problem ground-truth JSON, or a separate file can be maintained. To avoid changing the stable input of the current coverage evaluator, it is suggested to use a separate file first:

```text
benchmarks/frama-c-problems/requirements/requirements_100_code_only_contracts.json
```

The following schema is suggested for each record:

```json
{
  "id": 1,
  "path": "pointers/swap.c",
  "requirement_en": "...",
  "function_signature": "void swap(int *a, int *b);",
  "code_only_contract": "/*@ ... */",
  "contract_provenance": {
    "source_file": "benchmarks/frama-c-problems/ground-truth/pointers/swap.c",
    "source_function": "swap",
    "extraction_method": "target_function_preceding_acsl_block",
    "source_contract_hash": "...",
    "manually_modified": false
  },
  "contract_clauses": [
    {
      "id": "co1",
      "type": "requires",
      "expr": "\\valid(a)",
      "role": "verification_precondition",
      "source": "manual"
    }
  ],
  "coverage_target_ids": ["r1", "r2"],
  "auxiliary_contract_clause_ids": ["co1"],
  "excluded_reference_annotations": {
    "loop_invariants": 0,
    "loop_assigns": 0,
    "loop_variants": 0,
    "assertions": 0
  },
  "validation": {
    "syntax_valid": true,
    "reference_verifies": true,
    "verifier": "frama-c/wp",
    "timeout_seconds": 120
  },
  "notes": ""
}
```

### 4.2 Clause Roles

`contract_clauses` should explicitly distinguish two kinds of sources:

- `semantic_target`: the existing atomic ground-truth coverage clause;
- `verification_precondition`: an auxiliary condition added to form a reasonable, verifiable function interface, which should not in turn raise the requirement coverage score.

This distinction avoids mistakenly counting "providing sufficient call preconditions for the verifier" as semantic targets that the model should recover from the natural-language requirement, and it also makes it easier to report the composition of the oracle contract later.

### 4.3 Construction Principles

Each `code_only_contract` should satisfy:

1. include all applicable function-level clauses of the existing manual ground truth;
2. contain no reference implementation-level proof annotation;
3. not degenerate the task or make it vacuous through overly strong preconditions;
4. have frame conditions consistent with the requirement semantics, the function signature, and the reference behavior;
5. be ACSL-parseable and allow the reference implementation to verify while retaining its own internal proof annotations;
6. allow the contract text to be programmatically inserted by the pipeline and restored after repair;
7. have an auditable construction process, where added clauses must record role, source, and rationale.

### 4.4 Reference Contract Extraction Rules

The extractor should locate the target function using the `path` and `function_signature` in the dataset, and extract only the function-level ACSL block immediately preceding that target function definition. One cannot assume that the first or only ACSL block in the file is the target contract, because reference files may contain test functions, multiple annotations, or helper functions.

Extraction should preserve all legal function-interface contract structures:

- `requires`;
- `assigns`;
- `ensures`;
- `behavior` and `assumes`;
- `complete behaviors` and `disjoint behaviors`.

Extraction should exclude:

- `loop invariant`, `loop assigns`, and `loop variant` inside the function body;
- `//@ assert` or statement-level `assert`;
- test functions, `main`, and their proof goals;
- ghost state, helper lemmas, or proof skeletons bound to the reference control flow;
- maintenance notes such as `FIX` and `PROOF GOALS` in ordinary comments.

Extraction must be based on the target function's position and the ACSL/C structure, and must not simply use a regular-expression rule that "grabs the first `/*@ ... */` in the file." The first version may use a conservative parser plus structural validation; when unique localization is impossible, the problem should enter a manual-review queue rather than silently choosing a contract.

### 4.5 Alignment Between Reference and Atomic Ground Truth

An extracted reference contract cannot automatically become the final oracle just because it "once verified." Passing verification only means the reference implementation satisfies it; it does not guarantee that it is minimal, complete, and not overly constraining with respect to the requirement.

Each problem should also undergo:

1. decompose the reference function contract into clauses;
2. perform a bidirectional mapping with the existing `ground_truth_clauses`;
3. confirm that all applicable semantic targets are covered by the oracle contract;
4. mark extra memory safety, separation, frame, and other clauses as auxiliary interface conditions;
5. review whether extra `requires` are overly strong or make verification vacuous;
6. record manual decisions and rationale for inconsistencies.

A reference contract may be manually corrected, but the modification status, original hash, final hash, and reason for modification must be recorded in `contract_provenance` to keep the data-construction process auditable.

### 4.6 Meaning of Reference Verification

During data acceptance, the loop invariants and other proof annotations originally inside the reference implementation may be used, because this step only verifies whether the oracle contract is reasonable and is not a model evaluation.

These reference implementation annotations must be removed from the formal code-only generation input, and the reference code must not be provided. The model needs to regenerate its own implementation-level proof annotations.

## 5. C Code-Only Pipeline Design

### 5.1 Pipeline Input and Output

Input:

```text
requirement
function_signature
code_only_contract
optional type context
```

The output directory is suggested to keep the existing structure:

```text
<OUTPUT_DIR>/specs/...             # copied/frozen oracle contract artifact
<OUTPUT_DIR>/code/...              # generated or repaired C source
<OUTPUT_DIR>/reports/results.json  # verification and repair trajectory
```

Even if the oracle contract is not generated by the model, it should be copied into the run-specific `specs/` so that results are self-contained and reproducible and the contract-preservation check can reuse the existing mechanism.

### 5.2 Initial Code Generation

The new code-only prompt should make clear:

- the oracle `code_only_contract` must be placed verbatim directly above the function definition;
- the model may only implement the given signature;
- the model may choose the algorithm itself;
- the model should generate the necessary loop invariants, loop assigns, loop variants, and asserts according to its own control flow;
- implementation annotations should not be written into the function contract;
- the oracle contract must not be modified, deleted, reordered, or weakened.

In the main code-only setting, `code_annotation_hints` is suggested to be empty so that proof annotations are genuinely produced by the code-synthesis stage. If oracle proof hints are to be studied in the future, a clearly labeled auxiliary experiment may be set up separately and should not be mixed with the main code-only results.

### 5.3 Contract Preservation

One cannot rely only on the prompt to ask the model to preserve the contract. The C code-only pipeline should add programmatic enforcement:

1. read the canonical `code_only_contract` from the dataset artifact;
2. identify the target function definition;
3. delete or replace the ACSL function contract above the target function in the model output;
4. insert the canonical oracle contract;
5. extract the source contract and compare it with the canonical artifact;
6. if inconsistent or unable to insert safely, mark the problem as failed rather than verifying a contract rewritten by the model.

The Java and Python backends already have similar contract-enforcement mechanisms; the C backend can reuse their design ideas, but it needs to use a C signature/ACSL parser and must not rely on fragile arbitrary regular-expression substitution.

### 5.4 Verification and Repair

The initial code is verified by Frama-C/WP. After a failure, two repair strategies can be run:

```text
simple:
  verifier log -> one repair candidate -> verify

vgcr:
  verifier log -> failure/subgoal plan
               -> multiple focused candidates
               -> verify candidates
```

Repair may modify:

- function-body logic;
- local variables and control flow;
- loop invariants/assigns/variants;
- statement assertions and necessary implementation proof annotations.

Repair may not modify:

- the function signature;
- the oracle function contract;
- the external type context;
- the requirement or benchmark input.

Contract enforcement should be re-run before each candidate is written and verified.

### 5.5 Suggested Experimental Paradigm

The code-only isolation experiment no longer needs CGS, because the oracle contract is already given. The main comparisons are:

```text
oracle-contract + generation
oracle-contract + simple repair
oracle-contract + VGCR repair
```

The two repair variants must reuse exactly the same initial code artifact. The initial code must not be resampled separately; otherwise the benefit of the repair strategy would be mixed with generation sampling variance.

If correspondence with the four full-chain paradigms is needed, the code-only results can be presented as an independent diagnostic table instead of being forced into the four groups `Direct/CGS/VGCR/CodeNova`. Under the oracle-contract condition, CGS has no spec-generation stage to enhance.

## 6. Metrics and Reporting

### 6.1 Main Metrics

The suggested main code-only metrics include:

- initial code validity rate;
- post-repair code validity rate;
- absolute repair gain;
- repair success among initial failures;
- verifier timeout/error rate;
- contract mismatch/enforcement failure count.

### 6.2 Auxiliary Metrics

The following can be reported further:

- average repair rounds;
- average verifier calls;
- VGCR candidate pass position;
- failure taxonomy;
- grouped results for loop-containing problems versus loop-free problems;
- whether the first generation includes loop invariant/assigns/variant;
- whether repair adds or modifies implementation-level proof annotations.

### 6.3 Relationship to Full-Chain Results

Full-chain results answer:

> Can the model start from the requirement, generate a correct contract, and implement verifiable code that satisfies that contract?

Code-only oracle-contract results answer:

> Once function-contract errors are controlled for, can the model generate the implementation and its proof annotations?

The difference between the two can be used to diagnose the specification-generation bottleneck, but cannot simply be subtracted and interpreted as a strict independent probability, because code-generation difficulty varies with contract strength, expression form, and implementation freedom.

## 7. Implementation Steps

### Phase 1: Construct Data

1. For the 100 C problems, read the requirement, signature, atomic ground-truth clauses, and reference source;
2. locate the target function by signature and extract the function-level ACSL block directly above it;
3. keep `requires/assigns/ensures/behavior` and exclude all implementation-level annotations;
4. align the extracted contract with the atomic ground-truth clauses and label the clause role;
5. manually review missing semantics, overly strong preconditions, extra verifier conditions, and extraction ambiguity;
6. record source/final hashes and rationale for necessary modifications;
7. generate the separate `requirements_100_code_only_contracts.json`.

### Phase 2: Data Validation Tool

Implement a deterministic validator:

- validate the schema and id/path/signature alignment;
- check that the extracted contract is indeed adjacent to the target function and not to a test function or another ACSL block;
- parse `code_only_contract`;
- check that forbidden loop/statement annotations did not enter the contract;
- check that all coverage target ids trace back to the existing ground truth;
- check the completeness of the mapping among reference clauses, semantic targets, and auxiliary clauses;
- inject the oracle contract into the reference implementation;
- keep the reference internal proof annotations and run Frama-C/WP;
- output a per-problem validation report.

### Phase 3: Code-Only Generation

Add a separate CLI/wrapper to avoid turning the existing full-chain entry point into two tasks through complex flags:

```text
scripts/run_c_code_only_pipeline.py
scripts/run_openrouter_c_code_only_pipeline.sh
```

The first version can reuse the existing LLM client, verifier adapter, artifact layout, and repair strategy classes.

### Phase 4: Strict Incremental Repair

1. first run oracle-contract generation once, freezing `specs/` and the initial `code/`;
2. simple repair and VGCR repair each copy artifacts from the same source output;
3. record source artifact hashes;
4. verify that the oracle specs of the repair runs are exactly the same;
5. write all repair trajectories into `results.json`.

### Phase 5: Small-Scale Smoke Test

Before the formal 100-problem experiment, select 5 to 10 problems covering the following types:

- scalar, loop-free;
- pointer mutation;
- array traversal;
- loop invariant required;
- assigns/frame sensitive;
- overflow or memory-safety sensitive.

First verify that the data, contract enforcement, initial generation, simple repair, VGCR repair, and summary full chain all run, then extend to the full dataset.

## 8. Acceptance Criteria

Before entering the formal experiment, the following should hold:

- 100/100 code-only dataset entries pass schema validation;
- 100/100 oracle contracts can be parsed by Frama-C;
- reference implementations meet the pre-specified verification-pass criteria under the oracle contracts;
- oracle inputs contain no reference loop/statement proof annotations;
- contract enforcement is performed for the initial generation and all repair candidates;
- the canonical oracle contract hash is unchanged before and after repair;
- simple and VGCR use the same batch of initial code;
- missing outputs, API failures, and parse failures are all counted as failures against a fixed denominator;
- the report can distinguish generation failure, contract enforcement failure, verification failure, and timeout.

If the reference implementation of a problem cannot be verified under a reasonable oracle contract, the data problem should be fixed or flagged first; a pass must not be obtained by leaking the reference proof skeleton or adding unreasonable strong preconditions.

## 9. Risks to Be Specifically Avoided

### 9.1 Treating Reference Verification as a Proof of Semantic Sufficiency

A reference program passing Frama-C/WP only proves that the implementation satisfies the given contract; it does not prove that the contract fully expresses the requirement, nor that the preconditions are not too strong. The reference contract must be aligned with the atomic ground truth and undergo manual audit.

### 9.2 Oracle Contract Too Strong

One must not make the task trivial using preconditions that exclude legal inputs or directly fix internal state. Added preconditions must have a reasonable interface-level explanation and be recorded as auxiliary verification clauses.

### 9.3 Oracle Contract Incomplete

If frame, memory validity, or necessary normal-behavior conditions are omitted, verification failure may come from the data contract rather than the model's coding ability. Reference verification is a necessary dataset gate.

### 9.4 Leaking the Reference Algorithm

Any loop invariant, loop-bound evolution, ghost accumulator, or intermediate-array property may expose the reference control flow. Only the function-interface-level contract is retained in the formal input.

### 9.5 Contract Silently Modified by Repair

Prompt discipline is not enough to guarantee fairness. The canonical contract must be programmatically restored, and contract mismatch must be recorded as a failure in the summary.

### 9.6 Miscounting Auxiliary Conditions as Requirement Coverage

`code_only_contract` may be more suitable for the verifier than the coverage target, but added clauses should not in turn change the existing full-chain requirement coverage metric. The two data roles must remain explicitly separated.

## 10. Intended Paper Wording

It is suggested to describe this experiment as:

> To diagnose implementation and proof-synthesis capability independently of contract generation,
> we introduce a code-only setting with an oracle function contract. The oracle contains the full
> interface-level preconditions, postconditions, and frame conditions, but excludes all
> implementation-specific proof annotations such as loop invariants. Models must jointly synthesize
> the implementation and such annotations, while the oracle contract remains frozen throughout
> verifier-guided repair.

This setting is a diagnostic supplement to the full-chain main evaluation, not a replacement. The full chain remains the main task of the paper; code-only is used to answer how much of the bottleneck in code and proof-annotation generation remains once the correct function contract is known.
